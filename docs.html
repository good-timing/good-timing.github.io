What is Baton

Baton is actionable product analytics for MCP servers. When a customer's agent calls your server and your API can't meet the request, you often get a 200 with an empty body or a vague error — the customer's intent vanishes with no ticket and no trace. Baton captures that friction at the moment it happens: what the customer was trying to do, the call the agent made, what it expected, and what it got.

You instrument your server once. Whatever agent your customers use — Claude, Cursor, ChatGPT — keeps working exactly as before.

Quickstart

Pick the one that matches what you run. All three emit the same events in the same wire format to the same sinks, so the choice is about where the code goes, not what you get. Nothing below needs an account, and nothing leaves your machine.

baton-sdk goes inside a server you own, and captures your real customers. Requires Python 3.11+.

Step 1 · install

pip install "baton-sdk[fastmcp]>=0.8.8"

Step 2 · instrument

Two lines: the import, and the call. Tools registered before or after it are both captured.

from fastmcp import FastMCP
from baton import install_baton, VendorConfig

mcp = FastMCP("Acme Knowledge Base")
install_baton(mcp, VendorConfig(
    vendor_id="acme-kb",
    tenant_id="acme",
    vendor_display_name="Acme Knowledge Base",
))

@mcp.tool
def search_orders(customer: str) -> dict:
    return {"order_id": "o_123", "status": "shipped"}

Step 3 · run it

Leave out sink and events go to stderr as JSON Lines, one per line.

python server.py 2>events.jsonl

Step 4 · verify

One tool call produces three events — tool_call_start, tool_call_end, and a surface_snapshot describing the server. The first, formatted:

  "tenant_id": "acme",
  "vendor_id": "acme-kb",
  "session_id": "sdk-01a0a8cb-d946-721f-8291-60f3a785e7c6",
  "sequence_number": 1,
  "captured_at": "2026-09-16T05:58:46.863008Z",

  "agent_runtime": "mcp",

  "runtime_meta": {"io.modelcontextprotocol/protocolVersion": "2026-07-28", ...},

Abridged. runtime_meta carries the client's whole handshake block, and a few transport fields are left out. Every key shown is one the SDK emits, with the values from that run.

The four intent fields are null here because the call came from a script, not an agent. When an agent makes it, call_intent and call_expected carry what it was trying to do, call_workflow the wider task, and intent_source records which route supplied them — injected_param for a value the agent typed into an injected parameter, unset when it came from an annotation call — see MCP integration.

baton-proxy wraps a server you did not write, as a subprocess. Use it to see what Baton captures before instrumenting anything. Requires Python 3.11+, and nothing to install.

Step 1 · wrap the server

Put the proxy in front of the command your MCP client already runs, in that client's config. uvx fetches it per run.

{
  "command": "uvx",
  "args": ["baton-proxy", "--", "python", "server.py"]
}

Step 2 · choose where events go

In the same entry — not your shell. The client starts the proxy and passes it a fixed environment allowlist (six names on macOS and Linux), so an exported BATON_EVENT_SINK never reaches it.

"env": { "BATON_EVENT_SINK": "file:///tmp/baton-proxy.jsonl" }

Step 3 · use it

Drive a few tool calls from your client.

scan is a different route rather than a continuation of this one. Point it at an entry you have not wrapped: it wraps one temporarily, drives a headless agent at it, and writes its own report. It refuses an entry that already launches the proxy, and it ignores the sink from Step 2 in favour of a temporary file of its own.

uvx baton-proxy scan --config <server-name>

Step 4 · verify

A surface_snapshot lands at startup, then a pair per call. One tool_call_start, formatted:

The wrapped server is untouched: it receives the arguments it would have received unwrapped. What changes is the advertised schema, which gains the intent parameters, and the tool list, which gains baton_annotate.

How it fits together

The three capture paths emit the exact same events to a sink you choose; the difference is who drives them and where they live. The proxy is you, sampling your own server. The SDK is baked into your server (or your Skill), capturing real customer traffic. The gateway path sits one level up, in front of a fleet of servers you did not have to touch. Either way, the Baton Console is where that signal becomes a ranked roadmap your team can act on.

Each section has an architecture diagram: the Proxy, SDK and Gateway pages show how capture works; the Console page shows how it comes together across customers.

Stage 1 · Test  ·  sample friction yourself

Overview

baton-proxy wraps an MCP server and captures friction events. From Claude's perspective it is the MCP server; the real server is either its child process or the endpoint it forwards to. Your server receives the arguments it would have received unwrapped: the proxy adds three intent parameters to each tool's advertised schema and strips them from every call before forwarding.

Two upstream forms. A stdio server is named after -- and run as a subprocess; a remote Streamable-HTTP server is named with --url, with BATON_UPSTREAM_AUTH_TOKEN sent upstream as a bearer token. They are mutually exclusive.

uvx baton-proxy -- python server.py               # stdio, as a subprocess
uvx baton-proxy --url "https://mcp.example.com/mcp"  # remote, as a bridge
Requirements: Python 3.11+ · run via uvx (no install) or pipx · scan needs a server already configured in Claude (~/.claude.json).

The following diagram illustrates how the proxy sits between Claude and your server:

  • The proxy is the server, as far as Claude is concerned. Your real server runs as its child process and receives the arguments it would have received unwrapped.
  • Green marks what Baton owns — here the proxy and the Console. Everything neutral is yours or your client's, and none of it changes.
  • Three sinks, one event. The same envelope goes to stderr, a file, and an https:// collector; which ones are live is configuration.

Install

For a one-off scan, install nothing — uvx runs it on demand:

uvx baton-proxy scan --config <server-name>

To wrap a server permanently in Claude's config, put baton-proxy on your PATH so the config can invoke it directly:

pipx install baton-proxy

Plain pip install baton-proxy works if you manage your own Python env. Requires Python 3.11+. Currently 0.x — the wire format is stable and additive-only until v1.0; see the releases.

Quickstart

Replace your MCP server entry in Claude's config. The only change is wrapping your existing command:

// Before
{ "command": "npx", "args": ["@vendor/mcp-server"] }

// After — events go to stderr + /tmp/baton-proxy.jsonl
{ "command": "baton-proxy", "args": ["--", "npx", "@vendor/mcp-server"] }

Restart Claude and drive a few tool calls. Then see what happened:

// In conversation — ask Claude:
"Show me the friction report for this session."

// Or inspect raw:
cat /tmp/baton-proxy.jsonl | jq -c '{type: .event_type, payload}'

To ship events to a Console, add four env vars:

{
  "command": "baton-proxy",
  "args": ["--", "npx", "@vendor/mcp-server"],
  "env": {
    "BATON_EVENT_SINK":    "https://console.example.com",
    "BATON_TENANT_ID":     "your-tenant",
    "BATON_API_KEY":       "bk_live_...",
    "BATON_CONSENT_TOKEN": "customer-consented"
  }
}

scan

Preview friction on a server you already have configured — no permanent install, no change to your Claude config.

uvx baton-proxy scan --config my-server

scan reads the named entry from ~/.claude.json, reuses its credentials, drives a headless agent, and writes ./baton-report.md. Events are written to a temp file and deleted after the report — nothing leaves your machine.

FlagDescription
--config <name>Entry name in ~/.claude.json (required).
--config-file <path>Use a specific config file.
--timeout <seconds>Bound the run (default: 300s).
--out <path>Report output path (default: ./baton-report.md).

Startup guard: the proxy refuses to start when an https:// sink is configured but BATON_API_KEY is unset, or BATON_CONSENT_TOKEN or BATON_VENDOR_ID is still "local".

Remote servers

The proxy also fronts a remote HTTPS MCP server over the Streamable HTTP transport, instead of spawning a subprocess. It stays stdio-facing to Claude and forwards each message as an HTTP POST, streaming the JSON or SSE response back. Injection, emission and correlation are the same code as the subprocess path.

{
  "command": "baton-proxy",
  "args": ["--url", "https://mcp.vendor.example.com/mcp"],
  "env": { "BATON_UPSTREAM_AUTH_TOKEN": "..." }
}

--url and the -- <command> form are mutually exclusive.

Bridge scope today: the client-initiated request and response loop only. It does not open the standing GET SSE channel, so server-initiated messages (sampling, elicitation, notifications) are not captured, and requests are serialised. When the upstream is unreachable the handshake degrades to a synthetic healthy response rather than an error, so the client attaches and baton_annotate stays usable instead of the session wedging.

Injected tools

The proxy adds its own tools to the upstream server's tool list during the MCP handshake. The upstream server never sees them. baton_annotate is always there; the report tool depends on your sinks.

baton_annotate

Called by Claude (unprompted) when it hits friction. Emits an annotation event with signal_type, intent, suggested_improvement, and optional context. Available in all sink modes.

baton_session_report

Called when the customer asks "Show me the friction report for this session." Returns a markdown summary of the session. Needs a file:// sink to read from, which the default install has, so a stderr:-only install does not get it. Suppressed when an https:// sink is also present, which is the vendor production shape; set BATON_TENANT_TYPE=customer to keep it there.

What it captures

Per real tool call, three event types are emitted matching the Baton wire format:

EventPayload fields
tool_call_starttool_name, params
tool_call_endtool_name, result, duration_ms
tool_call_errortool_name, error_type, error_body, duration_ms

Each line in the events file is one JSON object — { event_type, payload }. A silent failure (a 200 that carried an error) lands like this:

{"event_type":"tool_call_start","payload":{"tool_name":"run_sql","params":{"statement":"ALTER TABLE orders ADD CONSTRAINT fk_customer FOREIGN KEY (customer_id) REFERENCES customers(id)"}}}
{"event_type":"tool_call_end","payload":{"tool_name":"run_sql","result":"200 OK — body: \"foreign keys are not supported\"","duration_ms":412}}
{"event_type":"annotation","payload":{"signal_type":"failure","intent":"add a foreign key so an order can't reference a missing customer","suggested_improvement":"reject unsupported DDL with an error instead of a silent 200"}}

Intent parameters

This is how the proxy captures why a call was made, not just what happened. At tools/list it adds three string parameters to every upstream tool's advertised schema. The agent fills them in as it composes each call, and the proxy strips them at tools/call before forwarding.

ParameterCaptured as
user_goaltool_call_start.payload.call_intent
expected_resulttool_call_start.payload.call_expected, omitted when the agent did not fill it in
overall_tasktool_call_start.payload.call_workflow — the task label sessions are grouped by, so it is only useful when the agent repeats the same string across a task

In the default mode, user_goal is the one advertised in each tool's required list. That is advertisement only: a call that omits it is served exactly as it would be unwrapped, and call_intent is simply null. Measured on proxy 0.6.8, a wrapped tool's schema lists ["customer", "user_goal"] as required where the unwrapped one listed ["customer"].

A parameter description reaches the model at the moment it composes the call, on every client. Some clients drop InitializeResult.instructions entirely, so instructions alone are not a reliable channel. A tool that already declares a parameter of that name is left alone: its value is forwarded untouched and never read as intent.

Fail-open: if injection or stripping raises, the message is forwarded unmodified. A bug in intent capture cannot break a tool call.

Trust & security

  • Open source, Apache 2.0. github.com/good-timing/baton-proxy
  • Fail-open. A Console outage never breaks the MCP pipe. Emission is enqueued on a background thread.
  • Outbound-only. The proxy never accepts inbound connections.
  • No external dependencies. Pure stdlib — no pydantic, no httpx.
  • Credential isolation. BATON_* vars are filtered from the upstream subprocess env.

Stage 2 · Deploy  ·  capture friction from your customers

Overview

baton-sdk is native instrumentation for vendors who control their MCP server source. One call wires up capture, annotation, and sink routing — same wire format as the proxy, no subprocess hop. Because it lives inside what you ship, it captures friction from your real customers, who never have to install anything.

MCP middleware path

Your MCP server calls install_baton(mcp, dsn=…). Two lines. Captures every tool call at the transport boundary and adds the annotation tool. Best for vendors with MCP servers as their primary surface.

Library API path

Code that calls your API wraps each call in client.trace(…). Same event envelope, same sinks — different emission boundary. Best for vendors who ship Skills rather than an MCP server.

baton-sdk is open source under Apache-2.0; the source lives in the baton repo. The Python package needs 3.11+. There is a TypeScript SDK too, @goodtiming/baton-sdk on npm, which takes the same DSN and emits the same events; everything on this page applies to both unless it says otherwise.

Install

Quickstart

The SDK runs in-process inside your server and captures every tool call at the transport boundary — no subprocess, your tools unchanged.

The following diagram illustrates where the SDK runs inside your MCP server:

  • No second process. The SDK is a library inside your server, so there is nothing extra to deploy, supervise or keep alive.
  • Capture is at the transport boundary — the tool name, params, result and error that crossed MCP. The SDK does not reach into your logs or your database.
  • The sink is yours to choose, and it is the only thing that leaves the process.

That string is the whole configuration. It is the DSN for one server, and it carries four things: a publishable key (baton_pk_…), the host events go to, your workspace id (ten_…) and the server's id (srv-…). The SDK reads all four and builds the sink itself.

install_baton works out which library your server comes from, and raises TypeError before changing anything if the object is not an MCP server it supports. Tools registered before and after the call are both captured. It adds one tool to your server, named after it: a server called "Acme Knowledge Base" gets acme-knowledge-base_annotate.

Getting a DSN

Sign in at baton.goodtiming.ai/account and press Add a server, with a name if you want one. The page shows the new DSN with a Copy button, and every server's DSN stays listed under Publishable keys. The setup agent makes one for you when it wires up a server.

We assign the server id and it never changes. The name is a label on /account and in your workspace picker, and you can rename it there. A publishable key can only write events, and only for the server its DSN names, so it is safe in your source.

Where the DSN goes

A server you distribute — a stdio server started on your user's machine — takes the DSN in source, as above. An MCP client starts a stdio server with a fixed allowlist of environment variables (six names on macOS and Linux) plus whatever the user wrote in their own client config, so a value in your .env never reaches it.

A server you host can read it from the environment. Set BATON_DSN and pass nothing:

install_baton(mcp)  # reads BATON_DSN

An explicit dsn= wins over BATON_DSN, and either one wins over BATON_VENDOR_ID and BATON_TENANT_ID, so a new DSN is never overridden by values an earlier install left in the environment.

A bare baton_pk_… key in place of the DSN stops at startup with a message saying to copy the full value from /account. A secret baton_sk_… key in a DSN works, and logs a warning: it reads and writes everything in your workspace, so it must never ship.

Without a DSN

To send to your own collector, or to try the SDK before you have a key, name the parts. Leave out sink and events go to stderr as JSON Lines.

import os
from baton import install_baton, VendorConfig
from baton.sinks import HttpSink

install_baton(mcp, VendorConfig(
    vendor_id="acme-kb",
    tenant_id="acme",
    vendor_display_name="Acme Knowledge Base",
    sink=HttpSink("https://collector.example.com", api_key=os.environ["COLLECTOR_KEY"]),
))

vendor_id names the server and tenant_id names the account the collector authenticates. One account holds many servers, so giving both the same value merges every server in it into one. HttpSink posts to {url}/v0/events with the key as a bearer token.

A VendorConfig can carry a DSN too — VendorConfig(dsn=…, scrubber=…) — when you want a DSN and other settings. Passing a DSN alongside vendor_id, tenant_id or sink raises, because the DSN already sets them.

Turning capture off

Set BATON_DISABLED=1 in the environment of the process that runs the server, and the SDK installs nothing: no wrapped tools, no annotation tool, no change to the server instructions, no collector connection, no background thread. The server runs as it would without the install_baton line. The SDK reads the variable once at startup, never writes to stdout, and never stops the server from starting, even with a config it would otherwise refuse. Any value other than empty, 0, false, no or off turns it on.

The switch belongs to whoever runs the server.

  • A server you distribute runs on your user's machine, so the switch is theirs. It goes in the env block for your server in their MCP client's config file, not in their shell: the client passes the server a fixed allowlist of environment variables, and an exported BATON_DISABLED is not on it.
  • A server you host runs on your machine, so the switch is yours. Your users cannot set it, and there is no per-user opt-out.
{
  "mcpServers": {
    "acme-knowledge-base": {
      "command": "acme-kb-mcp",
      "env": { "BATON_DISABLED": "1" }
    }
  }
}
If you tell your users about this switch, tell them where the variable goes. Someone who sets it in their shell has a server that is still capturing.

Library API

For vendors whose customers reach the API via agent-generated code (Skills pattern). Here Baton lives in the Skill code, not in a server — so it fits vendors who have no MCP server at all.

The following diagram illustrates where the SDK sits on the library path:

  • Your API is untouched. Baton lives in the Skill that calls it, not behind it, so nothing ships on the API side.
  • One client.trace(...) per call is the whole integration; the events it emits are the same envelope the MCP path emits.
  • Use this path when you ship a Skill rather than an MCP server.

TypeScript

The same SDK for Node. @goodtiming/baton-sdk emits the same envelope as the Python package to the same sinks, so a workspace can run both and the Console never learns which one produced an event. Node 20+.

npm install @goodtiming/baton-sdk

Your MCP server is the argument, as in Python. Both major versions of the official TypeScript MCP SDK are supported and both are optional peer dependencies, so you install whichever one you already use — @modelcontextprotocol/sdk 1.x or @modelcontextprotocol/server 2.x — and nothing else.

import { McpServer } from "@modelcontextprotocol/server";
import { withBaton } from "@goodtiming/baton-sdk";

const server = new McpServer({ name: "acme-knowledge-base", version: "1.0.0" });

withBaton(server, {
  dsn: "https://baton_pk_...@baton.goodtiming.ai/ten_.../srv-...",
});

Config fields are the Python names in camelCase — vendorId, tenantId, vendorDisplayName, intentParamMode, scrubber — and a dsn replaces the first three exactly as it does in Python. Tools registered before or after withBaton are both captured, and so are tools added or removed later.

What it captures

The same three intent parameters, the same annotation tool, the same surface_snapshot, and the same events. intentParamMode defaults to "required", which advertises user_goal in each tool's required list and never enforces it — measured identical to the Python SDK and the proxy on the currently published versions.

PII scrubbing is on by default here too, a rule-for-rule port of Python's ruleset. Pass identityScrub to opt out, or your own (value: unknown) => unknown. Read what it does and does not catch before relying on it.

What is not here yet

Stated so you find out now rather than later. None of it blocks the paths above.

  • Only StdoutSink and HttpSink. FileSink and MultiSink are deferred; the Python package has all four.
  • Only the high-level McpServer. The low-level Server is not wrapped.
  • Intent parameters need a Zod schema. On the 2.x SDK a tool registered with a non-Zod standard schema is still wrapped and still emits tool_call_*; it just advertises no intent parameters.
  • The per-request createMcpHandler shape is unscoped. It builds a fresh server per request, which would make the session id and the snapshot dedup request-lifetime state.

Wire compatibility

This is a tested property, not an intention. Both SDKs are checked against baton-spec, a neutral schema repo: every event type is validated against the shared JSON Schema, and the TypeScript emitter is diffed field-by-field against captured Python output for the same scenario. Envelope and payload keys must match exactly; values match except for ids, timestamps, timings and the genuinely language-specific fields.

PII scrubbing

Scrubbing is on by default. baton.scrub.Scrubber walks every event payload before it reaches the sink and redacts email addresses, Bearer tokens of 16 or more characters, sk- keys, AKIA access keys, JWTs, North American phone numbers, and card numbers that pass a Luhn check. It also redacts the whole value of any field named email, phone, ssn, api_key, token, secret, password or user_name.

It matches patterns. It does not find every piece of personal data. {"name": "Jane Doe", "address": "12 Elm St"} passes through unchanged, and a card number written with spaces or hyphens is not caught. Decide what your tools put in their arguments and results with that in mind.

To turn it off:

from baton import install_baton, VendorConfig
from baton.scrub import identity_scrub

install_baton(mcp, VendorConfig(dsn="https://baton_pk_...@baton.goodtiming.ai/ten_.../srv-...", scrubber=identity_scrub))

Stage 2 · Deploy  ·  capture a whole fleet at once

Overview

For fleets of MCP servers. The other two paths instrument one server at a time: the SDK goes inside a server you own, the proxy wraps a server you do not. This one captures at the gateway itself, so every server behind it is covered at once, and neither your clients nor your backend servers change.

Baton runs as a processor beside your gateway, on the gateway's external-processor hook for MCP. Traffic still flows client to gateway to server. Baton sees the MCP messages as they pass and never becomes a hop in the path: it is not a subprocess wrap and not an HTTP bridge.

The following diagram illustrates where Baton sits relative to your gateway:

  • Your gateway keeps the traffic. Client to gateway to server is unchanged; Baton is not inserted between any two of them.
  • The hook hands Baton a copy. The external-processor call is what Baton sees. Configure that hook fail-open and a Baton outage costs you the event, not the call.
  • Every server behind the gateway is covered at once, and none of them ships a change.

This is the path that reaches surfaces with no code to instrument. A client behind the gateway is captured without anyone shipping a change to it.

Quickstart

There is no package to install yet. The proxy and the SDK are published and you can start with either one today; the gateway processor ships with a runbook for your platform team instead, and we set it up with you. Talk to us and we will size it against your gateway.

Configuration

Two pieces: one hook in your gateway's own policy, pointed at the processor and set to see both the request and the response of each tool call along with its session id, and the same handful of environment variables the proxy reads.

VariablePurpose
BATON_VENDOR_IDLabels the captured signal.
BATON_EVENT_SINKWhere events go: the Console over https, your own object store, a file, or stderr. Comma separate to fan out.
BATON_API_KEYBearer token for the Console sink, from your secret store.
BATON_CONSENT_TOKENPer install consent. The processor refuses to ship anywhere remote while this is still the placeholder.

Nothing has to leave your walls. Point the sink at your own storage and the Console never sees an event.

Identity

This path resolves the caller from a request header, and which header is configuration rather than code. The value is hashed inside the processor and the raw identity never leaves your network, exactly as on the other two paths.

It needs two settings, and both matter: the header, which your gateway must pass on every call, and the hashing key, BATON_PRINCIPAL_ID_HMAC_KEY. A call without the header is captured with no caller, and nothing reports it. Without the key, the processor logs one warning and sends every event with no caller.

What it captures

Two parameters are added to the tool list the gateway returns: the agent's goal, and the result it expects. The agent fills them in on the next call. Baton reads them off that call and strips them before the request reaches your server, so your tool schemas and your handlers are unchanged and your customers never see them.

MCP messageWhat Baton does
tools/listAdds the two intent parameters to the response.
tools/call requestReads the values off the request, strips them, emits tool_call_start.
tools/call responsePairs the result with its call and emits tool_call_end or tool_call_error, with the duration.

The events are the same wire format the other two paths emit, so one Console reads all three. A response carries no request id, so the gateway passes the session id to the processor on both halves of each call, and results pair within a session in the order calls were made. Pairing is exact while a session's calls complete in order. Calls running at the same time inside one session can pair with the wrong request, and a call with no session id gets no result event.

Scrubbing runs in the processor before any sink sees an event, with the same patterns as the SDK.

Trust & security

Capture never breaks a tool call. The gateway is configured in fail-open mode on this hook, so if the Baton processor is slow, restarting or gone, the call goes through and the event is the only thing lost. Observation is best effort by design. Your traffic is not.

The proxy and the SDK capture friction for free. The following diagram illustrates how one Console gathers many customers:

Every event your proxy or SDK emits to an https:// sink lands in the Console under your tenant. There it's deduped across customers and ranked into trends, so you see the demand, not one transcript at a time.
