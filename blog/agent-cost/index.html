Research

MCP builders often ask us about the cost of asking agents why they called a tool. So we measured it.

Ujwal Chinthala, Good Timing  ·  November 18, 2026

When an agent calls your MCP server, you see the call. You don't see why the agent made it. Several tools, ours included, fix this the same way: they add one extra field to each tool and ask the agent to fill it with what the user is trying to do.

That field is not free. The agent has to read it and write it. Nobody we could find publishes what it costs. Here is what it costs, what you get for it, and the data behind it. We measured in Claude Code, mostly on a support desk we built for testing: a small ticket system with 7 tools, where the agent does tasks like "comment on every open P1 ticket". The full setup is at the end.

What we add, and why

Baton adds one field, user_goal, to each of your tools. The agent fills it like this:

1: read P1 ticket 2; success is full ticket details and comments

The number says which user message the call serves. The rest says what the call is for and what a good result looks like. Baton strips the field before your tool runs, so your code never sees it.

This is how you learn what people were trying to do when a call failed, or when it "worked" and still gave them nothing useful. Errors and latency can't tell you that.

What it costs

The field costs in two places. Only one of them costs time.

The writing, on every call. About 40 output tokens and 0.2 s per call on Sonnet. This is the cost the user feels. The agent spends longer writing. It doesn't think longer, and the tools take no longer.

The tool list, in money only. Each tool's description grows by about 130 input tokens. Input tokens cost money but almost no time. With tool search on, Claude Code's default, the client loads a description only when the agent needs it.

The trade

That is the price. In return you learn, for every call, what the user was trying to do and what a good result would have been. Nothing else gives you that.

You choose who pays it

You don't have to put the field in front of every caller. You can add Baton only for the customers, test servers or onboarding flows you pick. Everyone else sees your server exactly as before: no field, no 0.2 s. For the callers you pick, you can change what Baton asks of the agent, group by group, without a redeploy.

What we cut

The first version asked for three fields: the goal, the expected result and the overall task. We merged them into one field with a fixed shape: number, goal, "success is …".

Three things we tried that did not help:

  • Asking for fewer words. "At most 8 words" cut the field by only about 21 tokens, about 0.1 s. Other wordings barely moved it. The agent writes about as much as it needs.
  • Making the field optional. Agents fill an optional field anyway, every time we tested. You save a few tokens of description and nothing else.
  • Asking for the goal only on the first call of a message. It saved only about a fifth, and the later calls lost their goal.

What did work was fewer fields. Time follows the tokens written.

With tool search on, the two arms ran in turn. With it off, the no-Baton runs ran an hour after the Baton runs. So we compare only writing time and tokens, which repeat across days, and not wall time. Total input is higher with tool search on, in both arms, because each tool search is an extra request that resends the conversation.

Either way, that is about 40 tokens and 0.2 s per call on Sonnet. The agent spends more time writing. It does not think longer, and the tools take no longer.

The tool list. Each tool's description now includes the field: roughly 130 input tokens per tool, one short instruction included. With tool search off, the client sends every description on every request. On the 7-tool support desk, Baton then adds about 970 tokens to each request, and that grows in a straight line with the number of tools (we checked up to 281). With tool search on, Claude Code's default, the client loads a description only when the agent searches for it, and Baton adds about 110 tokens to the first request. Over the 5 tasks, Baton added about 8,200 input tokens with tool search on and about 20,200 with it off.

Input tokens cost almost no time: about 0.02 ms each, and 0.01 ms when cached. Adding 1,636 tokens of unrelated text didn't change how long the agent took to write. So this part costs money, not time.

How others do it

We are not the first to ask the agent why. PostHog, AgentCat (was MCPcat) and Alpic all add a similar field, on by default. PostHog and AgentCat ask for 15–25 words. None of them publishes what the field costs. Our data says two things about the common advice:

  • A word limit doesn't buy much. A limit keeps the field easy to read, but asking for fewer words barely changed what the agent wrote.
  • The tool list isn't the main cost. Most published tool-cost numbers count tokens in the tool list. For a field like this, the cost the user waits for is the writing on every call.

How we measured

The setup behind every number above, and what the numbers do and don't cover.

  • Client: Claude Code (claude -p), with only our test server connected and its other built-in tools turned off. Claude Code's tool search is on by default. Most of our runs had it off, so every tool's description loaded upfront. We repeated the main comparison with it on. We did not measure Cursor, ChatGPT, VS Code or any other client.
  • Model: Claude Sonnet 5.5 for most runs. We also timed Opus 5.5 and Haiku 5.5.
  • Servers: two small test servers we wrote. The main one is a support desk: a ticket system with 7 tools for finding, reading and changing tickets. Its tasks take 3 to 17 calls, such as "comment on every open P1 ticket". The other tracks a pantry (4 tools).
  • Comparison: the same tasks, with and without the field, run in turn so slow API minutes hit every arm.
  • What we read: tokens and timings from the client's own stream, per request and per call.
  • Size: 5 to 16 runs per task per arm. We report medians. That is small, so we only trust differences that repeat.
  • What repeats: token counts repeat to within a few tokens. Writing time repeats across days. Whole-task wall time does not: it swings ±50% with API load, so we don't draw conclusions from it.

Each experiment is written down before it runs, with its pass rule set in advance.

What we haven't measured yet: other clients and larger real servers. We'll publish those when we have them.
